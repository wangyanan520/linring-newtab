## 三、问题清单

### P0 — 静默数据损坏，应立即修复

#### P0-1 编辑表单重复 ID：连续编辑两条导致数据错位损坏，且完全静默

**位置**：`settings.js:302-333`（`showEditBookmarkForm`）、`settings.js:370-399`（`showEditCategoryForm`）

**三个缺陷叠加**（逐行核实）：
1. **缺旧表单清理**。`showAddBookmarkForm`（`settings.js:274-276`）有 `oldForm.remove()`，两个编辑表单**都没有**。
2. **表单元素本身没有 `id`**，而 `clearInlineForms`（`settings.js:148-154`）的列表是 `['bookmarkForm','categoryForm','itemForm','editItemForm']` ——不含编辑表单，切 tab 也兜不住。
3. **表单内部使用固定全局 ID**：`#editBmTitle`/`#editBmUrl`/`#saveEditBookmark`（`settings.js:314-316`）。

**实测（扩展模式 + 真实点击，即生产条件）**：

```
两个编辑表单就绪: #saveEditBookmark=2  #editBmTitle=2
最自然的用户路径: 改了 A → 点开 B → 回头点"保存"（想保存 A）

执行顺序:
  updateBookmark(bm_01, AAA_MODIFIED)   ← 监听器 L1（正确）
  updateBookmark(bm_02, AAA_MODIFIED)   ← 监听器 L2 也读了第 1 个输入框
最终数据: ["百度","AAA_MODIFIED",...]
pageerror: []        console 相关输出: []      ← 完全静默
```

**A 的修改丢失，B 被写成 A 的输入值，用户无从察觉。**

**机理（三段）**：
1. 第二次 `showEditBookmarkForm` 中 `document.getElementById('saveEditBookmark')` 按文档顺序返回**第一个**（属于 A），闭包 `id=B` 的监听器 L2 被绑到 **A 的按钮**上——**B 的保存按钮完全没有监听器**。
2. 点 A 的按钮时 L1、L2 依次启动。L1 在 `await chrome.storage.local.get(...)`（**真异步跨进程 I/O**）处让出，此刻**微任务队列为空**，检查点无事可做 → L2 立即同步读取 `document.getElementById('editBmTitle').value`，**表单尚未被销毁**，读到第 1 个输入框的值。
3. 两个 `updateBookmark` 基于**同一份快照**并发读-改-写，后写者覆盖先写者。

**行为随条件反向**（这是它极难被发现的原因）：

| 存储后端 | 事件类型 | 数据损坏 | 报错 |
|---------|---------|---------|------|
| **chrome.storage（用户实际）** | **真实点击** | **是** | **无** |
| chrome.storage | 合成 `click()` | 是 | 无 |
| localStorage（preview / CI） | 真实点击 | **否**（L2 抛 TypeError 中断） | TypeError |
| localStorage | 合成 `click()` | 是 | 无 |

**修复**（约 6 行）：给两个编辑表单设 `id` 并加入 `clearInlineForms`；创建前移除同名旧表单；改用 `form.querySelector` 获得局部作用域。

> **附带**：`renderBookmarks()`/`renderCategories()` 重建列表 `innerHTML`，**任何**重渲染（保存/删除/排序/导入）都会销毁用户正在填写的内联表单。

### P1 — 功能不可用 / 输入丢失

#### P1-1 超时只保护到"响应头"，慢网络即可让时钟延迟、挂起可致永久停摆

**位置**：`weather.js:247-252`、`calendar.js:154-159`

```js
const timeoutId = setTimeout(() => controller.abort(), 5000);
const response = await fetch(url, { signal: controller.signal });
clearTimeout(timeoutId);            // ← 响应头一到就撤销超时
if (!response.ok) throw new Error('Weather fetch failed');
const data = await response.json(); // ← 此处再无超时保护
```

- **挂起**：body 停顿 → `json()` 长期挂起 → catch 不触发 → 降级与重试**不可达**。天气永久停在"获取天气中..."；**时钟**因 `main.js:14 await Calendar.init()` 永不返回而 `main.js:15 App.startClock()` 永不执行，`#datetime` **永久空白**。
- **慢但正常的网络**：`calendar.js:118-128` 两年 × 两源**串行**、每 URL 6 秒超时，最坏 **24 秒**时钟不显示——**不需要任何异常网络条件**。
- **附带**：`clearTimeout` 未在 `finally`，`fetch` 抛错时被跳过，遗留待触发定时器。

> **置信度说明**：本项为**代码事实 + 逻辑推演，未做运行时复现**。代码事实（`clearTimeout` 位置）确凿；"挂起后永不恢复"依赖 `json()` 在 body 未结束时挂起的标准行为，未实测。

**修复**：`clearTimeout` 移入 `finally`；body 读取加超时；**把 `App.startClock()` 从 `Calendar.init()` 等待链上摘下来**。

---

#### P1-2 切 tab 后，被编辑行的操作按钮永久消失

**位置**：`settings.js:69`、`settings.js:148-154`、`settings.js:460`

`showEditItemForm` 用 `actions.replaceWith(form)` 把该行按钮整体替换成表单；切 tab 时 `clearInlineForms()` 删除表单，**被替换的按钮不会恢复**，`switchTab('categories')` 也不重新渲染。

**实测（扩展模式）**：编辑前按钮 1 → 表单显示 → 切走再切回 → 按钮 **0**、表单 **0**，用户只能关面板重开。

#### P1-3 打包产物混入测试代码

**证据**：`dist/*.zip` 含 `scripts/__tests__/` 下 4 个文件约 48KB。

**根因**：`pack.js:23-27` 的 `isJunk()` 不含 `__tests__`；`pack.js:150-151` 的 `verifyZip()` 断言"源码未全部入包即报错"，**把必须包含测试文件固化成正确行为**。

#### P1-4 "可复现打包"名不副实：SHA 依赖文件 mtime

```
node scripts/pack.js  → c2a14661e8499cc2f338e610a7d1bb67fb2f926e99293dff8ce2241033b1005f
```

**根因**：`pack.js:77` 用文件 `mtime` 编码 DOS 时间戳。**不能作为跨环境发布指纹。**

# 附录 A：第一轮对抗式复审（结论已被附录 B 推翻）

> 方法：运行时复现攻击 + 事实核查 + 定级复核 + 措辞审查。**A.1/A.2 已失效**，保留以记录过程。

## A.1 初版 P0-1 机理描述错误

初版称"点 A 的保存会同时触发两个监听器，两者都读到 A 输入框的值，**B 被静默写成 A 的值**"。

第一轮在 **localStorage 预览模式 + 真实点击** 下复现，得到：
```
最终数据 = ["AAA_FIRST","知乎",...]      ← 第 2 条未被写坏
pageerror: Cannot read properties of null (reading 'value')
```
据此判定：L1 保存后 `renderBookmarks()` 销毁表单，L2 读到 `null` 抛错中断，**没走到写 B** → **定级由 P0 下调为 P1**。

**该结论错误**（原因见附录 B）：复现虽用了真实点击，但跑在 localStorage 后端上，而这恰是唯一不损坏数据的组合。

## A.2 定级复核（已撤销）
P0 → P1 的下调**已撤销**，最终维持 P0。

## A.3 措辞修正 2 处（有效）
1. 初版"项目称需 GUI，本次实测跑通"暗示项目说法有误——实际项目说法**正确**，本报告只是在 GUI 环境下确认其成立。已改。
2. 初版称农历库"**指向** lunar-javascript"是**推断**而非验证。已改为"**疑似**……未与上游比对"。

## A.4 遗漏补报 1 项（有效）
`renderBookmarks()`/`renderCategories()` 重建 `innerHTML`，**任何**重渲染都会销毁用户正在填写的内联表单。已并入正文 P0-1。

## A.5 优势章节复核（有效）

# 附录 B：第二轮对抗式复审（修正附录 A）

> 攻击点：第一轮复现所用条件是否等价于生产环境。**结论：附录 A 的核心修正错误，已撤销。**

## B.1 攻击思路
第一轮复现跑在**预览模式**（`localStorage`），而用户实际用扩展（`chrome.storage.local`）。两者异步特性完全不同：前者是微任务级，后者是真异步跨进程 I/O。而 P0-1 的机理依赖"L1 让出后、L2 读 DOM 前"这个窗口——**后端延迟不同，窗口内发生的事情不同，结果可能相反**。

## B.2 条件矩阵实测

| # | 存储后端 | 事件类型 | 数据结果 | 报错 |
|---|---------|---------|---------|------|
| 1 | localStorage | 真实点击 | `["AAA_FIRST","知乎"]` 完好 | **TypeError** |
| 2 | localStorage | 合成 click | `["百度","AAA_FIRST"]` 损坏 | 无 |
| 3 | chrome.storage | 合成 click | `["百度","AAA_FIRST"]` 损坏 | 无 |
| 4 | **chrome.storage** | **真实点击** | `["百度","AAA_FIRST"]` **损坏** | **无** |

**组合 4 是真实用户场景 → 数据静默错位损坏。**

- **组合 1 为何不损坏**：localStorage 立即 resolve，L1 续体在微任务检查点跑完并销毁表单，L2 读到 `null` 抛错中断——**异常"救"了数据**。
- **组合 4 为何损坏**：跨进程 I/O 需数毫秒，L1 让出时微任务队列为空，L2 立即读到尚未销毁的表单。
- **组合 2/3 为何损坏**：合成 `click()` 的监听器调用之间不插入微任务检查点。

## B.3 撤销清单
P0-1 定级 P1 → **P0**；机理改为"L2 读到第 1 个输入框并写入 B，两个并发写互相覆盖"；报错情况改为"真实场景下**无任何报错**"。

## B.4 新增结论
**N2**：CI 只跑 `--preview`（localStorage），而 P0-1 恰是"仅在 chrome.storage 出现且完全静默"的缺陷。

## C.1 复验结果：其余结论在生产条件下全部成立

| 结论 | 原验证条件 | 第三轮复验（扩展模式） | 结果 |
|------|-----------|---------------------|------|
| P1-2 切 tab 按钮消失 | preview | 按钮 1 → **0** | ✔ 成立 |

| P0-1 最自然触发路径 | 合成/真实点击混杂 | 改 A → 点开 B → 回头保存 A → `["百度","AAA_MODIFIED"]` | ✔ 成立 |
| P0-1 "完全静默" | 未单独验证 | 相关 console = `[]`，pageerror = `[]` | ✔ 成立 |

**结论：条件依赖是 P0-1 的特例（因它涉及时序窗口），不是普遍现象。** P1-2/P2-2 是纯 DOM/逻辑行为，与后端无关——这也说明第二轮"所有结论都要怀疑"的过度反应没有必要，**正确的做法是区分"涉及时序的结论"与"不涉及时序的结论"**。

## C.2 复验中发现的新错误 1 处（性能数据失真 4–6 倍）

初版与续版的性能数据均在 **preview 模式**下测得，却被当作项目性能陈述：

| 指标 | preview（初版引用） | **扩展模式（真实）** | 偏差 |
|------|-------------------|-------------------|------|
| FCP | 44–84ms | **236–268ms** | 约 4 倍 |
| 书签可见 | 54–67ms | **327–352ms** | 约 5 倍 |
| 时间可见 | 295–312ms | **346–709ms** | 约 1.7 倍 |

**结论方向不变**（仍远优于 3s），但**数字不实**。已更正正文，性能评分由 9.5 调整为 9。

## C.3 复验中发现的新遗漏 1 项（比第二轮结论更根本）

第二轮把 P0-1 的逃逸归因于"CI 存储后端与生产不同"。**第三轮发现更根本的原因**：

> **E2E 的 56 项断言中，没有任何一项涉及"编辑"操作。**

已逐条列出全部 53 个具名断言核实：覆盖了渲染、主题、组件开关、排序（上移）、导入导出、备份恢复、协议白名单、日历、快捷键、隐私、天气、CSP、审计——**唯独没有编辑书签/分类/链接**。

因此 P0-1 是**双重逃逸**：
1. **操作序列未被覆盖**（根本原因）——即使 CI 跑扩展模式也不会触发；
2. **即使覆盖了，preview 后端下行为相反**（第二轮的发现）——会抛 TypeError 而非静默损坏，可能被误判为偶发失败。

**且**：E2E 有一条 `[14] 无 pageerror` 守卫断言。它之所以一直通过，正是因为不覆盖编辑路径。**这条断言的存在反而制造了"异常已被监控"的错觉**（正文 P2-7）。

## C.4 为何老是反复

三轮里同一个缺陷得到了三种结论。原因分四层：

### 第一层：技术操作失误
1. **单点采样**。每轮只测一个条件组合，看到结果即下结论，从未主动枚举条件空间。
2. **默认选择最方便的环境**。preview 模式无需 GUI、跑得快、CI 也在用，具有"权威感"——但它系统性偏离生产（本轮再次证明：性能差 4–6 倍）。
3. **未先问"这个结论依赖哪些隐含条件"**。P0-1 依赖"存储后端"与"事件类型"两个维度，而这两个维度**在出问题的那几行代码里完全看不出来**——它们在存储层的异步实现和浏览器的事件派发机制里。

### 第二层：方法缺陷
4. **用一个单点观察推翻另一个单点观察**。第一轮看到 preview 下数据完好，就直接推翻 P0，而没有问"为什么与预期不同？是什么条件造成的？"
5. **复现带来的虚假信心**。"我跑了测试"让推翻原结论变得理直气壮，但**测试条件的代表性从未被检验**。
6. **确认偏误**。初版倾向给出有冲击力的结论；第一轮倾向"纠正"；第二轮倾向"再纠正"——每轮都在追求"我发现了真相"的完成感，而不是"我的结论在什么条件下成立"。

### 第三层：问题本身的性质
7. **这个缺陷是条件依赖的，且依赖条件是隐藏的、非局部的**。代码的局部阅读无法暴露它；任何单点实测都只是条件空间里的**一个采样**。而我把采样当成了总体。
8. 这也解释了为什么它同时逃过了项目自审（静态阅读 + E2E 全绿）和我的前三轮：**它们都是单点验证**。

### 第四层：元层——最诚实的一点
9. **我在报告里批评项目"E2E 全绿给了虚假信心"，而我自己的复现犯了完全相同的认识论错误**：把"我验证过了"等同于"结论可靠"。
10. **反复不是态度问题，是流程缺失**。缺少的那一步是：*下结论前先问"如果这个结论是错的，最可能是因为什么条件？我测的是哪个组合？还有哪些组合没测？"*
11. **代价是可信度损耗**。读者看到 P0→P1→P0 会怀疑评估者。而每次反转其实都有证据——问题在于**证据的代表性没有被检验**。

### 正确做法（可复用）
- 严格区分三类陈述：**代码事实**（可信，如 `clearTimeout` 位置）、**单点观察**（必须标注条件）、**普遍结论**（必须条件矩阵支撑）。本报告初版把第二类当第三类陈述。
- 对**涉及时序/异步**的缺陷，强制做条件矩阵：存储后端 × 事件类型 × 运行环境。
- 复现条件**默认选最接近生产的那个**，而不是最方便的那个。
- **验证动作本身也要被验证**——这与项目自审漏掉 N1（键盘排序 `this` 解绑）是同一类问题的不同表现。

### 一个不全是坏消息的结论
反复最终收敛到了正确答案，并且**只有通过反复才挖出了 C.3 那个更根本的发现**（E2E 零编辑覆盖）。如果第一轮就在 preview 下"验证成功"并满意离开，报告的结论会错，且项目会带着"CI 全绿"的错觉继续。

**但这不是为反复辩护**：如果第一轮就做条件矩阵，一次即可到位，还能省下两轮的时间与可信度损耗。
